# 渲染与导出性能准则

适用所有工作流迁移。agent 必须审计原工作流，保留视觉、声音、时间、透明度与逐元素编辑能力，重写低效实现。默认优先复用，其次流水线，再对独立重任务做有界并行。不能以降分辨率、降帧率、删动效、把全部元素烘焙进单一视频来冒充优化。性能必须实测，未达预算就继续修改。

## 当前 TO DO 真实链路

- 调度在 server/production/runner.mjs。当前 voice/plan gate 各 2，asset 使用既有上限，subtitles 为 1。黑板手绘的 render 默认请求 2，按 CPU/可用内存限制为 1～4 个隔离 Python 进程；其他扩展仍为 1。预算是每个生产文档的上限，不是全应用跨文档的全局限流。详见 chalk-render-performance.md。Promise.all 不等于渲染已并行；其他扩展提高并发须实现资源合同、失败/取消与文档更新回归。
- src/lib/editGraph.ts 生成工程 EditGraph，electron/exportSequence.cjs 的 exportSequence 处理透明素材、文字预渲染、最终合成及声音。最终合成优先 todo-media-engine，失败回退 ffmpeg-cli；preferJs 只是强制后端选项，不代表更快。应走宿主导出接口。
- electron/chalkTextExport.cjs：静态文字缓存 PNG；动态文字连续推送 RGBA 到 ffmpeg rawvideo，遵守编码背压，透明中间层 qtrle/argb MOV。完整编排同段多镜合并烘焙，按 inPoint 切片复用，预览/导出使用同源绘制。
- 当前文字导出使用一个隐藏渲染窗口，按组/片段依次编码；不是任意多窗口或帧块并行。若实测此处为瓶颈，先实现独立上下文 worker 池与边界测试，再让扩展依赖新能力。

迁移时重新检查目标宿主代码，不能把上述并发数或文件名当作永远不变的接口。

## 如何处理 Python 逐帧合成

逐帧处理本身不一定错误，瓶颈通常是 Python 像素循环、每帧字体/SVG/对象重建、PNG 保存与读取、内存拷贝或反复启动编码器。先分别测布局、绘制、传输、编码和 I/O，不能仅凭“使用 Python”判断慢。

| 工作类型 | 优先评估的路线 |
|---|---|
| 剪切、拼接、缩放、裁剪、叠加、淡入淡出、音频混合 | Python 生成参数/滤镜图，FFmpeg 执行实际媒体处理；避免 Python 重绘已有视频每一帧 |
| 文字/形状/路径动画、打字机、镜头转角 | 复用 TO DO Canvas 时间采样渲染；缓存字体布局/路径，连续输出帧；复杂效果若需 GPU，应先验证宿主后端兼容性 |
| 像素计算、遮罩与图像处理 | NumPy 向量化或原生实现，避免 Python 双层像素循环；关注广播临时数组与内存代价 |
| 特殊科学/算法渲染必须逐帧计算 | 保留 Python 算法，预计算静态资源，按需用进程池或释放 GIL 的原生库，独立任务并行，原始帧流交给编码器 |
| GPU 模型/粒子/复杂着色 | 按实际 GPU/显存与模型能力评估原生/GPU 后端；硬件编码只加速编码，不会自动解决 CPU 绘制瓶颈 |

FFmpeg 过滤器与复杂滤镜图的官方说明：https://ffmpeg.org/ffmpeg-filters.html 、https://ffmpeg.org/ffmpeg.html 。Python 进程池：https://docs.python.org/3/library/concurrent.futures.html 。NumPy 广播：https://numpy.org/doc/stable/user/basics.broadcasting.html 。具体能力按项目安装版本验证。

## 必须审计的低效写法

| 原写法 | 改造要求 |
|---|---|
| 每帧新建浏览器、Canvas、字体、模型或 ffmpeg | 在任务/worker 生命周期初始化一次，复用，结束后释放 |
| 每帧 PNG 编解码、base64 往返，先保存全片图片再编码 | 接口允许时使用连续原始帧流；只有恢复/协议确有需要才落盘，并记录成本 |
| 每句重算整段布局、重渲背景与相同资源 | 共享对象/整段只算一次；局部片段引用时间窗口。缓存键包含字体、邻句、参数、画幅、种子与版本 |
| 静态保持段重复画几百帧 | 只生成一张图或缓存帧；持续动画仍正确更新 |
| 视觉变化导致全部 TTS/生图/镜头重做 | 分层缓存与失效；只重做受影响层 |
| 每个 worker 复制全量资源，整片帧全部驻留 | 复用只读资源，最少数据传输，有界任务/帧缓冲与及时释放 |
| 多次完整转码、元素各自混入配音 | 独立透明元素与独立声音层，尽量一次最终合成；增加中间转码须说明必要性 |

## 并行必须保持依赖与资源边界

可并行：互相独立的素材、镜头/元素渲染、只读固定输入的场景/帧块；可流水线：渲染 → 有界传输 → 编码。资源初始化可与无依赖准备阶段重叠。

必须等待：TTS 时间决定分镜、相邻句决定共享布局、最终合成依赖图层完成。同一编码器按帧号输出；同一 Canvas、浏览器窗口、文件名、随机数全局状态和工程 store 不得被多个任务同时修改。

先测 workers=1/2/4，按硬件和工作类型调整，选吞吐较高的稳定值，不能无限 Promise.all 或直接开满 CPU。CPU 密集 Python 纯字节码可评估进程池；I/O 或释放 GIL 的原生库可评估线程。GPU 显存/硬件会话、磁盘、ffmpeg 内部线程均计入预算，避免进程数乘线程数超额。

优先场景并行。帧级并行需无状态时间采样、独立上下文、固定种子/帧号、按序重排与有界输出。有递推物理/粒子状态时先预计算或提供状态快照；不能从任意帧直接重启。分块检查跨块转场、帧序、alpha、字体和音频，不能无脑拼接。

4K RGBA 单帧约 31.6 MiB，几十帧排队就占用数 GiB。限制最大在途任务/帧数，遵守编码器 drain 背压。取消与失败须停止生产、终止子进程并清理临时资源，不能留下后台任务继续修改文档。

有可安全并行的重任务却无理由串行，不满足迁移要求。无可安全并行阶段则提供测量与原因，不为了“并行”牺牲正确性。

## 性能验收与交付

固定素材/哈希、种子、字体、画幅、fps、时长、编码设置、画质及同一硬件。明确比较生成、图层渲染、最终导出或端到端，不能用一个最快子阶段对比原流程完整耗时。冷启动/热缓存分别至少测 3 次，用中位数；记录阶段耗时、帧数、有效 fps、峰值内存/显存、并发/编码线程、缓存命中、后端、版本和产物大小。

保留串行/并行对比，测吞吐与资源曲线，选择稳定并发点。同步验证预览/导出一致性、时长/音画同步、alpha、编辑能力与块边界；速度更快但质量失败仍判 FAIL。优化前约定耗时、资源与回退预算；不能见失败后只提高预算。硬件不同则重新建立基线。

extension.check.json 必须加入性能检查，生成 PERFORMANCE.json 并校验预算。脚本 scripts/check-render-performance.mjs 校验实测报告和质量证据文件；格式见 docs/templates/render-performance.json。它不代替真实 benchmark 或视觉/音频断言，模板默认不能通过。原流程没有独立基线的新开发扩展也应保留串行参考实现与预算。

在 MIGRATION.md 写出原瓶颈证据、依赖关系、复用/缓存、并发和线程预算、背压/取消、冷热基线对比、质量断言、选定后端与不可并行理由。明确已实现/已验证/仅计划，未达预算继续修复，真实环境缺失如实报告阻塞，不能伪造加速倍数。
