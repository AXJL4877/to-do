# 黑板手绘渲染优化与实测

本次改造保留透明 WebM、定格 PNG、笔尖轨迹以及时间轴上独立可编辑的元素。未引入 GPU 绘制；最终合成仍走宿主导出接口。

## 已实现

- 手绘只计算元素周围的局部工作区。边缘留出揭示半径，平移对齐原网格与笔画排序周期；输出 crop 不变，笔尖转回原画幅坐标。
- 同一镜头复用渲染器类和缩放后的手图。保留现有按输入/参数失效的图层缓存。
- 独立镜头在独立 Python 进程中并行；每个镜头使用独立手图文件名。每个镜头内的元素按原顺序处理。
- 默认请求两个 worker，按 CPU 和可用内存收缩，最多四个。每个进程限制 OpenCV/BLAS 与 FFmpeg 线程，避免并发数乘内部线程过量。
- 停止时不再启动排队节点，等待已启动节点收尾再返回停止；节点失败后其他已启动节点收尾，重试复用成功缓存。

`TODO_RENDER_CONCURRENCY=1` 可用于串行运行，值 2～4 用于请求更多并发；最终仍受预算限制。预算只作用于单个生产文档，多文档同时生成时资源占用会叠加。内存预算使用保守估算并留出 1 GiB，不是操作系统硬内存限额，也不是实测峰值 RSS。

## 固定样例的实测

同一机器、同一素材与编码设置：两个 1280×720 镜头，每镜头两个手绘元素，12 fps；每种方案三次冷 Python 进程，取中位数。计时包括进程初始化、绘制、VP9 编码和定格提取，不包括测试解码验收、TTS、生图或最后的工程合成。

全画幅参考通过当前代码的参考开关运行原绘制算法；三种方案均限制 VP9 为两个线程、原生计算为一个线程，并使用当前手图复用逻辑。这是控制变量比较，不是未经修改的旧宿主默认线程设置实测。

| 方案 | 耗时中位数 |
|---|---:|
| 原全画幅算法，单镜头并发 | 28.90 秒 |
| 局部工作区，单镜头并发 | 17.63 秒 |
| 局部工作区，双镜头并发 | 9.30 秒 |

组合约为原样例的 3.11 倍速度，耗时减少约 68%。这不是所有工程或完整视频端到端的加速承诺：元素填满画幅时局部裁剪收益小，少镜头无法充分并发，4K 或低内存设备可能降为串行。

所有九轮实际产物的解码 BGRA 像素、定格图、crop、帧数、时间与笔尖轨迹一致，另有 alpha 非空与透明角落断言。独立核心回归覆盖横屏中心、横屏边缘和竖屏；工作数组总字节减少约 75%～86%，不包含整个进程/编码器内存。原帧算法使用 `TODO_CHALK_FULL_CANVAS=1` 作为参考，默认使用局部路径。

## 可执行回归

在 TO DO 源码根目录运行，Python 必须具备现有黑板依赖（OpenCV、NumPy）。测试使用固定合成素材，不调用付费服务。

```powershell
python scripts/test-chalk-render-performance.py
node scripts/test-chalk-concurrency.mjs
python scripts/benchmark-chalk-pipeline.py
npm run chalk:enter
npm run production:test
npm run skills:check
npm run export:test
npm run build
```

核心逐帧对比或实际编码产物不一致时立即失败；benchmark 还要求局部串行中位数快于全画幅参考。并发脚本验证 CPU/内存限额、文件隔离、失败收尾、重试缓存与取消排队。实际测量保存在 `native/test-output/chalk-pipeline/benchmark.json`；核心对比在 `native/test-output/chalk-performance/`。真实编码基准耗时数分钟，未测热缓存/进程树峰值，不作为完整扩展迁移的 PERFORMANCE.json 认证。

## GPU 的后续判断

先采用已经验证的局部计算和双镜头并发。现有实现仍用 CPU 绘制和透明 VP9 编码；使用硬件编码不会自动加速这些笔画计算，且不能假定硬件编码保留 alpha。若代表性长片仍慢，应分别采集绘制、管道传输、透明编码、中间转码和最终合成的耗时，再决定是否将遮罩/合成迁移到 GPU。此次整体测量无法证明剩余瓶颈一定在编码或绘制，不能凭总耗时决定重写。

更新源码后重启开发中的 TO DO 后端/应用才能加载调度修改。已发布安装版需重新构建发布；单独重新安装 `.todoext` 不会替换宿主代码。已有缓存仍可复用，新生成或参数改变的镜头使用优化路径。
